# PR #114 review against issue #67 design and improvement plan

Reviewed head: `f4614c89aa6501095dcb0e84ef0e4453c18f9772`.
Recommendation: request changes. Stage A improves the mapper substantially, but its legality gate is incomplete.

## Project goal and architectural interpretation

The current goal in CLAUDE.md and the M9 canonical architecture is an out-of-tree MLIR compiler whose canonical tile-centric `micro` execution IR supports AI-chipset performance evaluation and automatic scheduling. The earlier CPU-focused ARCHITECTURE.md describes the retained validation pipeline, not the full current scope. AVX2 is the first validation backend. Semantics, scheduling and target lowering remain separate; tensors survive structured optimization until bufferization, and SIMD is explicit.

The mapping chain is extraction → rule matching → placement → connection synthesis → covering search → binding → verification. Machine topology and target policy come from YAML and LLKMap/target packages. Generic mapping code must remain target-neutral. Search intent persists in search-space IR; selected plans must retain enough concrete endpoint/resource identity to reproduce legality, materialization and cost.

PR #114 declares Stage A only. Full tile materialization, joint route exploration, selected target lowering, numeric invocation and compile/tune integration remain B/C work. Their absence alone is not a defect in this PR, and this PR cannot close issue #67.

## Confirmed findings

### 1. [P1] Reject conflicting requirements on the same endpoint instead of dropping the layout

Location: `lib/Mapping/CoveringSearch.cpp:183–187`.

`boundSolvedLayoutForPort` returns null when two solutions for one port disagree. The caller consequently treats the port as having no layout requirement. This still produces a legal-looking direct connection while discarding explicit obligations. Stage A A2 says: “Do not turn ambiguity into ‘no layout’. Duplicate requirements for one endpoint must agree or reject the candidate.” The rule grammar also describes `require layout` as a requirement, not an implicit disjunction.

Reproduction: reuse `repeatedOperandGraph`, `kRepeatedConflictRules`, `transformMachine` and `kTwoLayouts`; change the consumer's blocked requirement from operand1 to operand0. Operand0 now requires both plain and blocked. Search returns **one plan with one Direct connection serving two endpoints**, rather than rejecting the conflicting candidate. `Review114.ConflictingRequirementsOnOneEndpointMustReject` fails on the PR implementation.

Return an explicit conflict or reject the candidate before connection synthesis. If alternate layouts are intended, enumerate a concrete choice with its own identity instead of erasing both requirements.

### 2. [P2] Require solved-layout assignments when the selected rule needs them

Location: `lib/Mapping/PlanBinder.cpp:1497–1498`.

Semantic layout validation runs only if the entire `layout_parameters` attribute exists. Removing that attribute bypasses every assignment completeness/domain/constraint check while retaining the layout-family names. The verifier returns success without knowing the concrete layout selected by the plan. A4 permits rebuilding an absent map from a complete legal assignment, but explicitly says missing or ambiguous assignments cannot pass executable verification.

Reproduction: bind the existing AVX2 fixture, remove `layout_parameters` from the vector's `micro.mapping`, retain all other metadata, then call `verifyMappedMicroIR`. It returns success. `Review114.MissingLayoutAssignmentMustReject` fails.

The PR body acknowledges this deferral to B1. That is a deviation from A4's current merge gate, rather than evidence A4 is complete. Reject missing assignments for rules with layout requirements now, or explicitly restrict legacy/partial verification and revise the completion claim. Also validate completeness per occurrence when one family serves several ports; the current family-level existence test cannot establish that every occurrence has an assignment.

### 3. [P2] Tie a movement's actual SSA source to its recorded connection/value

Location: `lib/Mapping/PlanBinder.cpp:653–659`.

The new provenance check accepts any producer in the same kernel that carries `micro.mapping` or `micro.connection`. It never checks that this producer/result is the value recorded by the connection, or that a preceding hop belongs to the same connection and has the expected hop index. The earlier value check compares two metadata integers, not either integer to the actual SSA operand. A5 explicitly requires matching source/destination endpoints and actual SSA uses; it also says not to relax verification for ambiguous old metadata.

Reproduction: bind the existing movement fixture; clone the mapped producer before the original; redirect the binder-emitted copy's operand to the clone's result, leaving the original route/value/connection/hop stamps unchanged. The module remains structurally valid, both producers are mapped, and `verifyMappedMicroIR` returns success. `Review114.WrongMappedSSASourceMustReject` fails. This demonstrates that an unrelated mapped value can borrow a connection's stamps and receive the completeness exemption.

Resolve the stamped value/producer endpoint against the actual workload binding; for subsequent hops verify the same connection and predecessor hop. Selected-consumer validation must likewise inspect uses rather than just integer attribute types. Persist any identity needed to perform these checks instead of accepting unprovable provenance.

## Plan comparison

| Task | Assessment |
|---|---|
| A1 | PortRef and per-occurrence identity are introduced in the transient model. Persistence remains B1. |
| A2 | Distinct operand uses retain layouts; equal uses can share. Conflicting requirements on one occurrence still disappear: finding 1. |
